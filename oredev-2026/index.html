    Building the tool

    Building the tool

    A structured command for the AI tool is basically a good definition of what you want to build and why.

    CContext: define the research goals and constraints. What problem are you solving? What are the limitations?
    RRole: specify the expertise level and perspective. Who is performing this task?
    AAction: describe the specific task to complete. What exact steps should be taken?
    FFormat: specify the output format and structure. How should the result be delivered?
    TTarget audience: define who will use or consume this. Who is the end user?

    Choosing how to test

    You still choose how to test

    Classic methods still work. The AI-built tool gets its discipline from them; it does not replace them.

    Classic methods

    Moderated sessions, interviews, card sorting, paper prototypes.

    Proven. Needs people and time.

    This talk

    AI-built tool

    Built and adapted with Claude, runs async on the real product.

    Fast. Depends on an AI provider.

    Local model or your own build

    An open model on your own machines, or no AI at all.

    Predictable. Data stays in-house.

    Need safety and predictability? Use a local model, or build the whole tool yourself.

    Choosing how to test

    What AI does right now

    It makes us faster. It also makes us depend on things we do not control.

    It speeds us up

    • Working prototypes in hours
    • Analysis drafts in minutes
    • Less busywork for researchers
    • Tools that change with the product

    It creates dependencies

    • A provider you do not control
    • Models and prices that change
    • Data that leaves the building
    • Downtime that stops your study
    The result: a move toward local models has already started.

      Best practices

      • Use structured, constraint-driven prompts and iterate in small increments. Test early, validate AI outputs immediately, and treat AI as a collaborator, not a decision-maker.
      • Start with clear assumptions and hypotheses. Choose research methods based on what you actually need to learn, and understand what each method truly measures.
      • Measure observable behavior, not opinions alone. Combine quantitative and qualitative insights, and keep tasks realistic, focused, and unbiased.
      • Prototype failures are cheaper than production failures. Automate repetitive work, not critical thinking. Data alone is not insight; interpretation still matters.
      • New AI proposes targets, the researcher owns them. Write them down before the data arrive.
      • New Label generated data everywhere it appears, and never let a draft skip human review.

      Prompt tricks

      When working with Figma Make, use clear and structured prompts to get the best results:

      Start with context:
      “Perform the following changes...”
      End with constraints:
      “Do not change anything else.”

      This approach ensures precision and prevents unintended modifications to your prototype.

      2026 With Claude: say what the tool may decide by itself and what the researcher decides. “Suggest targets, but never overwrite a value I set.”

      Prompt for Claude

      The same CRAFT idea, written in tags an agent can parse. Run it in Claude Code inside your product’s repository. Replace the CAPITALS.

      <context>
I am a UX researcher. We run unmoderated, async usability tests on PRODUCT NAME,
the web app in this repository. Participants: PARTICIPANT TYPE, NUMBER people,
about SESSION LENGTH minutes each, screen and voice recorded.
We have no dedicated researcher, so the tool must guide the study set-up as well as the session.
</context>

<role>
Act as a senior UX researcher and a front-end developer who knows this codebase.
</role>

<hypotheses>
H1: HYPOTHESIS 1
H2: HYPOTHESIS 2
</hypotheses>

<task>
Build a usability test tool in this repository, next to the product. It has three parts:
1. Builder: read the product code and propose one or more tasks per hypothesis that use what
   the product can really do today. Suggest targets for each task (success rate, median time,
   SEQ) and flag task briefs that name menu items or describe the steps.
2. Participant view: welcome and consent, then each task on the real product with a side panel
   (brief, "I'm done", "I give up", think-aloud reminder), then questions after each task:
   orientation check, SEQ (1-7) and confidence (1-5). Finish on a page that exports the results.
3. Results: compare every metric with its target per task and per hypothesis
   (Met / Partly / Missed) and export ZIP, CSV and JSON.
Add a small tracking probe to a test build of the product that reports clicks, dead clicks,
navigation and visible errors to the tool. Keep it out of production builds.
</task>

<rules>
- Never overwrite a target I set; show your suggestion next to it.
- Never record typed text, only the kind of key pressed.
- Label generated example data as examples wherever it appears.
- The tool must also work without an AI connection.
- Ask me before adding a new dependency.
</rules>

<format>
Work on a new branch. Add a README that explains how to run a study.
When you are done, list the tasks you created, the hypothesis each one tests,
and anything in the product you could not test.
</format>

<audience>
Researchers and designers set up the study. PARTICIPANT TYPE take it on a desktop,
often with little time and mixed English skills.
</audience>
